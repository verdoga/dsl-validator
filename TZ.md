# ТЗ-инструкция: локальный валидатор сценариев DSL

## 1. Назначение и приоритет источников

Реализуй локальное настольное приложение для Windows, которое находит сценарии DSL в выбранном каталоге, разбирает каждый сценарий внешней библиотекой `dslparser`, запускает совместимые с версией документа библиотечные диагностики и сохраняет отдельный JSON-отчёт рядом со сценарием. Предоставь управление через локальный сервер и HTML-интерфейс.

Применяй источники требований в следующем порядке:

1. настоящая ТЗ-инструкция;
2. фактический публичный API и поведение `dslparser` на закреплённом коммите;
3. `DSL v1.1.md` — правила языка, необходимые будущим диагностикам;
4. `Diagnostics.md` — пример каталога для проверки достаточности API валидатора, но не перечень диагностик к реализации в этой задаче;
5. `STM.html` — визуальный и accessibility-референс, но не источник предметной логики.

## 3. Границы результата

### 3.1. Реализуй

- один Windows `amd64` `.exe`;
- локальный HTTP-сервер на `127.0.0.1:8580` без выбора другого порта;
- рекурсивное обнаружение `.txt`-сценариев;
- определение версии каждого файла только через `dslparser`;
- последовательный конвейер разбора, запуска диагностик и формирования отчёта;
- версионируемый реестр диагностик;
- публичный read-only API валидатора для функций диагностик;
- библиотеку диагностик в корневом каталоге `Diagnostics/`;
- JSON-отчёты рядом со сценариями;
- серверные HTML-страницы списка, прогресса и отчёта;
- фильтрацию и сортировку записей отчёта;
- обработку всех штатных ошибок парсера и всех определённых ниже ошибок конвейера;
- тесты и документацию.

### 3.2. Не реализуй

- собственный DSL-парсер либо повторный разбор директивы версии;
- копию AST парсера с иной семантикой;
- реализацию 95 примерных диагностик из текущего `Diagnostics.md`;
- запуск диагностик при отсутствии `Document`;
- CLI для проверки файлов;
- редактор, просмотр или открытие исходного сценария;
- SPA, frontend-фреймворк, CDN либо сетевые ресурсы времени выполнения;
- многопоточную обработку файлов;
- отдельный технический журнал;
- автоматическое исправление сценариев;
- переход по символическим ссылкам, junction и иным reparse points;
- прикладное ограничение размера файла.

Внешний `dslparser` является единственной сторонней зависимостью приложения. Для остального кода используй только стандартную библиотеку Go. Встрой HTML, CSS и JavaScript в `.exe` через `embed`.

## 4. Архитектура проекта

Не меняй существующий module path проекта валидатора. В путях импортов ниже под `<module>` понимай значение директивы `module` из его `go.mod`.

Организуй код так:

```text
/

├── validatorapi/               # публичный контракт для библиотечных диагностик
├── Diagnostics/                # библиотека и композиция диагностик
│   └── <category>/             # подпакеты категорий по мере появления диагностик

├── internal/workspace/         # обход каталога и сопоставление отчётов
├── internal/pipeline/          # последовательная обработка файлов
├── internal/report/            # модель, JSON, схема и атомарная запись
├── internal/webapp/            # HTTP, состояние операции и серверный HTML
```

Соблюдай направления зависимостей:

- `cmd/validator` собирает зависимости и не содержит предметной логики;
- только `internal/parseradapter` импортирует `github.com/verdoga/dslparser`;
- `validatorapi` не импортирует парсер и не выполняет ввод-вывод;
- `Diagnostics` и все её подпакеты импортируют только стандартную библиотеку и `<module>/validatorapi`;
- `pipeline` зависит от адаптера, `validatorapi`, реестра диагностик и отчётов;
- `webapp` вызывает сервисы workspace/pipeline и не разбирает DSL;
- пакет отчётов не запускает диагностики;
- циклические импорты запрещены.

Добавь архитектурный тест на базе стандартных `go/parser` и `go/ast`, который проверяет границу импортов: ни один файл вне `internal/parseradapter` не должен импортировать `github.com/verdoga/dslparser`, а любой файл под `Diagnostics/` не должен импортировать пакет парсера прямо или косвенный адаптер.

## 5. Роль парсера и роль валидатора

`dslparser` является единственным компонентом, который:

- проверяет UTF-8;
- удаляет начальный BOM;
- делит вход на физические строки;
- триммирует края строк по `unicode.IsSpace`;
- читает обязательную директиву версии;
- выбирает реестр версии парсера;
- классифицирует конструкции;
- строит физические и логические области AST;
- создаёт фатальные и локальные синтаксические ошибки.

Валидатор не повторяет ни одну из этих операций. Он:

- открывает файл и передаёт `io.Reader` в `dslparser.ParseReader`;
- классифицирует возвращённый результат по контракту парсера;
- преобразует read-only AST в read-only представление `validatorapi`;
- передаёт это представление функциям диагностик;
- собирает ошибки парсера, штатные срабатывания диагностик и ошибки самого конвейера в единый отчёт;
- управляет версиями диагностик, файлами, отчётами и интерфейсом.

Не считывай первую строку отдельно и не применяй регулярное выражение к `@dsl-version`. Выбранная пользователем версия не передаётся парсеру и не подменяет версию документа.

## 6. Публичный API валидатора для диагностик

Размести контракт в пакете `<module>/validatorapi`. Не раскрывай через него типы `dslparser`. Диагностика должна компилироваться без импорта парсера и без доступа к файловой системе.

### 6.1. Базовые значения

Определи именованные значения:

```go
type Version string
type Severity string
type Source string
type ParserCode string
type NodeKind string
type ElementKind string
type BodyMode string

type Position struct {
    Line   int
    Column int
}

type Span struct {
    Start Position
    End   Position
}
```

Зафиксируй значения `Severity`: `error`, `warning`, `recommendation`. Зафиксируй значения `Source`: `parser`, `diagnostic`, `validator`. Координаты начинаются с единицы, столбец считается в Unicode-кодовых точках, конец `Span.End` исключён.

Зафиксируй строковые значения представления AST и отобрази на них одноимённые константы парсера в адаптере:

- `NodeKind`: `step`, `heading`, `tag`, `text`, `block_boundary`;
- `ElementKind`: `field`, `token`, `body_line`, `separator`, `group`;
- `BodyMode`: `opaque`, `structural`.

Объяви в `validatorapi` константы `ParserCode` для всех 20 строк раздела 14. Не импортируй ради них парсер: адаптер преобразует `dslparser.DiagnosticCode` в строковый контракт и отдельно проверяется тестом на полное совпадение каталога.

Предоставь `Span.Valid()` и функцию вычисления поддиапазона по индексам Unicode-кодовых точек в переданной строке. Не вычисляй столбцы по байтам UTF-8.

### 6.2. Read-only представления

Предоставь следующие интерфейсы; реализации держи внутри адаптера:

```go
type ParserIssue interface {
    Code() ParserCode
    Message() string
    Span() Span
    RelatedSpan() (Span, bool)
}

type Block interface {
    OpenSpan() Span
    CloseSpan() (Span, bool)
    Span() Span
    Closed() bool
    Mode() BodyMode
}

type Element interface {
    Kind() ElementKind
    Name() string
    Raw() string
    Value() string
    Span() Span
    Parsed() bool
    ParserIssues() []ParserIssue
    Children() []Element
}

type Node interface {
    Kind() NodeKind
    Raw() string
    Value() string
    OriginalName() string
    CanonicalName() string
    HeadingLevel() int
    Span() Span
    Parsed() bool
    Synthetic() bool
    ParserIssues() []ParserIssue
    Elements() []Element
    Children() []Node
    Block() (Block, bool)
}

type Document interface {
    VersionRaw() string
    Version() Version
    VersionSpan() Span
    Roots() []Node
    ParserIssues() []ParserIssue
}
```

Возвращай новые срезы, не раскрывай изменяемые коллекции и не добавляй setters. Сохраняй значения парсера без дополнительного тримминга и без изменения регистра.

Смысл строк:

- `Node.Raw()` — нормализованная парсером исходная строка с исходным регистром;
- `Node.OriginalName()` — исходное имя тега;
- `Node.CanonicalName()` — каноническое имя тега в нижнем регистре;
- `Element.Raw()` — исходное нормализованное значение с исходным регистром и экранированием;
- `Element.Value()` — разобранное парсером значение, которое для отдельных полей может быть снято с экранирования либо приведено парсером к нижнему регистру;
- `Document.VersionRaw()` и `Document.Version()` — исходная и каноническая формы версии.

Любая диагностика регистра обязана использовать `OriginalName` или `Raw`, а не делать вывод об исходной записи по `CanonicalName` или `Value`.

### 6.3. Контекст и навигация

Передавай диагностике `Context`, построенный только из готового AST:

```go
type Cursor interface {
    Node() Node
    Path() []int
    Depth() int
    Parent() (Cursor, bool)
    PreviousSibling() (Cursor, bool)
    NextSibling() (Cursor, bool)
    Children() []Cursor
    Ancestors() []Cursor
}

type Context interface {
    Document() Document
    Walk(func(Cursor) bool)
    PhysicalNodes() []Cursor
    NodesByKind(NodeKind) []Cursor
    NodesByCanonicalName(string) []Cursor
    ParserIssues() []ParserIssue
    HasParserIssue(ParserCode, Span) bool
}
```

Правила навигации:

- `Walk` обходит логическое AST в прямом порядке;
- `PhysicalNodes` исключает синтетические узлы и сортирует исходные узлы по началу диапазона, сохраняя детерминированный порядок при совпадении;
- `Parent`, siblings и `Ancestors` относятся к готовой логической вложенности AST;
- поиск по имени принимает только уже каноническое имя;
- `HasParserIssue` сравнивает код и точный полуоткрытый диапазон;
- вспомогательный обход элементов выполняй отдельной функцией `WalkElements(Node, func(Element) bool)` в `validatorapi`.

Не добавляй в API `SourceView`, исходные байты, полный текст файла, чтение пути, произвольный доступ к строкам файла либо повторный лексический анализ. Необходимые исходные фрагменты уже доступны как `Raw()` у узлов и элементов. Закрывающая граница блока доступна через `Block.CloseSpan()`.

### 6.4. Контракт диагностической функции

Определи:

```go
type Passport struct {
    Code        string
    Category    string
    Severity    Severity
    Title       string
    Description string
    Basis       string
    Reference   string
    BadExample  string
}

type VersionScope struct {
    All      bool
    Versions []Version
}

type Finding struct {
    Message     string
    Span        *Span
    RelatedSpan *Span
}

type Reporter interface {
    Report(Finding) error
}

type Check func(Context, Reporter) error

type Definition struct {
    Passport Passport
    Versions VersionScope
    Check    Check
}
```

Реестр при запуске обязан проверить:

- непустые код, категорию, название, описание, основание, эталон и неудачный пример;
- допустимый уровень;
- ненулевую функцию;
- взаимоисключение `All == true` и непустого `Versions`;
- непустой список конкретных версий при `All == false`;
- уникальность и каноничность версий;
- отсутствие двух определений с одним кодом в пересекающихся областях версий;
- уникальность кода в итоговом отчёте как идентификатора определения, но не запрет нескольких срабатываний одного определения в разных местах.

`Reporter.Report` проверяет диапазоны и сохраняет валидные срабатывания в порядке вызова. Одинаковые срабатывания одной функции с равными сообщением, основным и связанным диапазонами сохраняй один раз.

Запрети диагностике ввод-вывод, сеть, запуск goroutine, изменение глобального состояния и изменение AST. Диагностика выполняет только детерминированное чтение `Context` и выдачу `Finding`.

## 7. Библиотека `Diagnostics/` и версионирование

Размести композиционный пакет в корневой папке `Diagnostics/`; имя Go-пакета — `diagnostics`. Не переноси эту библиотеку в `internal`.

Каждая предметная категория размещается в отдельном подпакете и экспортирует функцию `Definitions() []validatorapi.Definition`, возвращающую свежую копию списка. Не создавай пакет на одну диагностику. Корневой пакет импортирует категории, объединяет определения в стабильном порядке и предоставляет:

```go
func All() []validatorapi.Definition
func ForVersion(validatorapi.Version) []validatorapi.Definition
func SupportedVersions() []validatorapi.Version
func Validate() error
```

Для текущей сборки `SupportedVersions()` возвращает только `1.1`. Порядок версий и диагностик должен быть стабильным и не зависеть от обхода map.

Одно определение может относиться:

- к одной версии: `Versions: ["1.1"]`;
- к нескольким версиям: один список без копирования функции;
- ко всем версиям: `All: true`.

Не дублируй функцию ради каждой версии. При добавлении версии DSL добавь её в каталог поддерживаемых версий и область существующих диагностик только после проверки совместимости их условий.

В рамках этой задачи не переноси 95 строк из `Diagnostics.md` в production-код. Создай инфраструктуру реестра и test-only определения, проверяющие контракт, выбор одной/нескольких/всех версий, порядок, ошибки регистрации и изоляцию сбоев.

## 8. Исключение дублей между парсером и диагностиками

Считай синтаксические ошибки, которые создал `dslparser`, окончательными ошибками источника `parser`. Не создавай для того же условия вторую запись источника `diagnostic`, даже если в примерном каталоге существует числовой аналог.

Собирай ошибки парсера в отчёт только из `Document.Diagnostics()`. Не обходи `Node.Diagnostics()` и `Element.Diagnostics()` для повторного добавления в отчёт: эти методы доступны диагностическим функциям только для определения локальной пригодности узла и предотвращения пересечений.

Для фатальной ошибки используй только `*dslparser.FatalError`. При ней AST отсутствует, поэтому никакие определения из `Diagnostics/` не выбираются и не запускаются.

Для локальной ошибки AST существует. Добавь ошибку парсера в отчёт, затем запускай диагностики подходящей версии для остальных проверок. Наличие локальной ошибки дочернего элемента не запрещает анализ других узлов. Диагностика, которой нужны корректные данные конкретного узла или элемента, обязана проверить `Parsed()` и связанные `ParserIssues()`.

Зафиксируй в документации библиотеки диагностик текущие пересечения примерного каталога:

| Примерные номера | Ошибка парсера или правило |
|---|---|
| `001` | `INVALID_UTF8` |
| `002`–`006`, а также регистр директивы из части `010` | `MISSING_VERSION` в разных входных формах |
| `013` | `EMPTY_TAG_NAME` |
| `015`–`016`, часть случаев `017` | `INVALID_BLOCK_OPEN` |
| часть случаев `018` | `INVALID_BLOCK_CLOSE` |
| `019` | `ORPHAN_BLOCK_CLOSE` |
| `020` | `UNCLOSED_BLOCK` |
| `021` | `UNCLOSED_QUOTE` |
| `042`–`043` | `MALFORMED_HEADING` |
| `053`, `078`, `167` | `UNSUPPORTED_TAG_FORM` |
| `054` | `ENDTASK_WITHOUT_TASK` |
| `056` | `STEP_OUTSIDE_TASK` |
| `057` | `SPEAKING_CONTEXT` |
| `086`, `172`, `175` | `MULTIPLE_SEPARATORS` |
| `171` | `MISSING_SEPARATOR` |
| `182` | `CONTENT_BEFORE_VARIANT` |
| `183` | `NESTED_VARIANTS` |
| `185` | `VARIANT_OUTSIDE_VARIANTS` |

Для полного совпадения не регистрируй числовую диагностику. Для частичного совпадения будущая реализация числовой диагностики обязана вызвать `HasParserIssue` и выдавать только остаточные случаи, которые парсер не отметил. Не заменяй более общий текст ошибки парсера более подробной диагностикой и не подавляй ошибку парсера.

Проверяй отсутствие пересечений интеграционными fixtures. Не вводи универсальную эвристику дедупликации по похожести сообщений.

## 9. Достаточность API для примерного каталога

Текущий `Diagnostics.md` содержит 95 примерных записей с номерами в диапазоне `001`–`231` и пропусками. Не называй его полным реестром и не утверждай, что в файле 285 реализуемых записей.

Покрой все 95 примеров следующими возможностями API:

| Возможность | Примерные номера |

## 10. Рабочий каталог и обнаружение файлов

На стартовой странице запроси:

1. абсолютный путь рабочего каталога;
2. режим версии в `select`: `Автоопределение` либо конкретная поддерживаемая версия; в текущей сборке конкретный вариант только `1.1`.

Проверь, что путь абсолютный, существует, является каталогом и доступен для чтения. Отклоняй корневой путь, если он является symlink, junction или другим reparse point.

Обходи каталог рекурсивно и последовательно. Ищи файлы с расширением `.txt` без учёта регистра. Не переходи по symlink-каталогам, junction и reparse points. На Windows проверяй атрибут `FILE_ATTRIBUTE_REPARSE_POINT`, а не только `os.ModeSymlink`. Ошибка одного подкаталога не останавливает сканирование остальных.

Сортируй сценарии по полному абсолютному пути без учёта регистра; при равенстве используй исходный полный путь как второй критерий.

Для каждого найденного `.txt` во время сканирования один раз вызови `dslparser.ParseReader`, чтобы заполнить столбец версии. Не извлекай версию иным способом. После сканирования не сохраняй AST как источник истины для будущего анализа: перед анализом файл может измениться, поэтому анализ открывает его и снова вызывает тот же парсер. Это два независимых вызова парсера в разные пользовательские операции, а не две реализации разбора версии.

В таблице файлов покажи минимум:

- полный путь;
- имя;
- размер в байтах;
- DSL-версию;
- состояние существующего отчёта и время последней проверки;
- доступные действия.

Показывай каноническое значение `Document.Version()` либо `Не определена`, если парсер не вернул документ или файл нельзя открыть. Локальные ошибки при существующем `Document` не мешают показать версию.

## 11. Поведение выбора версии

В режиме `Автоопределение` анализируй каждый файл по `Document.Version()` и выбирай `Diagnostics.ForVersion` только после успешного построения документа.

В режиме конкретной версии:

- всё равно получай объявленную версию только из `Document.Version()`;
- файл с совпадающей версией анализируй полностью;
- файл с успешно определённой другой версией пометь `Исключён выбором версии`, не запускай диагностики и не создавай/не заменяй его отчёт;
- файл с неопределённой версией либо иной фатальной ошибкой парсера обработай до минимального отчёта с ошибкой парсера, потому что иначе пользователь не получит причину отказа;
- файл, который нельзя открыть, также обработай до минимального отчёта валидатора, если отчёт физически возможно записать.

Кнопка анализа отдельного файла для несовпадающей, но успешно определённой версии должна быть недоступна с текстовым объяснением. `Проанализировать все` в конкретном режиме обрабатывает совпадающие файлы и файлы с неопределённой версией, а несовпадающие учитывает отдельным счётчиком `Исключено выбором версии`.

Наличие активного отчёта не исключает файл из операции. `Проанализировать все` заново обрабатывает каждый входящий в выбранный набор сценарий и заменяет его старый канонический отчёт после успешной сериализации.

Не запускай общеверсионные диагностики при фатальной ошибке версии. `All: true` означает все версии успешно построенных `Document`, а не файлы без версии.

## 12. Обнаружение и сопоставление отчётов

Считай кандидатом отчёта любой файл, имя которого без учёта регистра заканчивается на `report.json`, даже если перед суффиксом нет пробела или дефиса.

Новый отчёт для `lesson.txt` всегда записывай по каноническому пути `lesson - report.json` в том же каталоге. Имя вычисляй удалением последнего расширения исходного имени и добавлением ` - report.json`.

При сканировании декодируй кандидаты в строгую типизированную структуру. Не используй `map[string]any`. Проверь `schema_version`, обязательные поля, enum, диапазоны, сводные счётчики, абсолютный путь источника и согласованность `source_file.name` с basename пути.

Сопоставляй отчёт со сценарием по абсолютному очищенному пути и имени. На Windows сравнивай пути без учёта регистра. Не используй hash, inode либо содержимое как идентичность файла.

Если несколько валидных отчётов ссылаются на один сценарий, активным считай отчёт с наиболее поздним `analysis.finished_at`. При равенстве используй время изменения файла отчёта, затем полный путь по возрастанию. Остальные покажи в таблице конфликтных отчётов.

Не включай в основную таблицу отчёты, источник которых отсутствует. Покажи их в отдельной таблице вместе с повреждёнными, чужими, неподдерживаемыми и конфликтными отчётами. Для каждой строки укажи путь, стабильный код причины и сообщение. Покажи суммарное количество отклонённых отчётов.

Не изменяй и не удаляй отклонённые отчёты автоматически.

## 13. Последовательный конвейер анализа

Обрабатывай ровно один файл одновременно. Не создавай worker pool и не запускай диагностики параллельно.

Для каждого выбранного файла выполни стадии:

1. Зафиксируй время начала, путь и имя.
2. Повтори `stat`; получи актуальный размер для интерфейса.
3. Открой файл.
4. Вызови `dslparser.ParseReader` ровно один раз.
5. Классифицируй результат по контракту раздела 14.
6. При существующем `Document` создай `validatorapi.Context`.
7. Добавь в будущий отчёт `Document.Diagnostics()` как записи `source: parser`.
8. Выбери `Diagnostics.ForVersion(Document.Version())`.
9. Последовательно запусти каждое определение в стабильном порядке.
10. Проверь и добавь его срабатывания как `source: diagnostic`.
11. Преобразуй сбой отдельной функции в запись `source: validator` и продолжи следующие функции.
12. Отсортируй записи в исходном порядке, назначь номера и рассчитай сводку.
13. Зафиксируй окончание, длительность, статус и стадию отказа.
14. Полностью сериализуй отчёт в памяти.
15. Атомарно запиши или замени канонический файл отчёта.
16. Обнови состояние операции и только затем переходи к следующему файлу.

Не дописывай JSON частями. Не запускай диагностики, если парсер не вернул документ. Не считай штатное срабатывание диагностики ошибкой выполнения функции.

## 14. Контракт результатов `dslparser`

Обрабатывай результаты вызова строго так:

| `Document` | `error` | Обработка |
|---|---|---|
| ненулевой | `nil` | Допустимый полный или частичный AST; продолжи конвейер |
| `nil` | `*dslparser.FatalError` | Добавь одну parser-запись; статус `incomplete`, стадия `parsing`; диагностики не запускай |
| ненулевой | ненулевой | Нарушение контракта; `PARSER_CONTRACT_FAILURE`, источник `validator`; диагностики не запускай |
| `nil` | `nil` | Нарушение контракта; `PARSER_CONTRACT_FAILURE`; диагностики не запускай |
| любой | иной тип ошибки | `PARSER_UNEXPECTED_ERROR`, источник `validator`; диагностики не запускай |

Используй `errors.As` для `*dslparser.FatalError`. Не сравнивай сообщения ошибок.

Изолируй непредусмотренный `panic` только на границах вызова внешнего парсера и одной диагностической функции. Panic парсера преобразуй в `PARSER_PANIC` источника `validator`; panic диагностики — в `DIAGNOSTIC_PANIC`. Не используй `recover` в обычной предметной логике.

### 14.1. Все фатальные ошибки парсера

| Код | Условие в актуальном парсере | Обработка конвейером |
|---|---|---|
| `INVALID_UTF8` | вход не является корректным UTF-8 | версия `Не определена`; одна parser-запись без координат; `incomplete/parsing`; без диагностик |
| `MISSING_VERSION` | пустой вход; первая физическая строка после BOM и тримминга не имеет точной корректной директивы; отсутствует значение; имя слито со значением; присутствует пробел внутри значения/лишнее содержимое | та же обработка; сообщение бери дословно из `FatalError.Error()` |
| `UNSUPPORTED_VERSION` | `registry.ForVersion` парсера не знает каноническую версию | версия `Не определена`; parser-запись с сообщением парсера; без попытки анализировать файл как выбранную версию |
| `READ_FAILURE` | `ParseReader` получил `nil` либо `io.ReadAll` вернул ошибку | parser-запись; `incomplete/parsing`; исходную причину не переклассифицируй как validator-ошибку |

`FatalError` не предоставляет диапазон. Не придумывай строку и позицию; сохраняй `location: null` и показывай `Позиция не определена`.

### 14.2. Все локальные ошибки парсера

| Код | Смысл | Дополнительное поведение |
|---|---|---|
| `EMPTY_TAG_NAME` | после `@` отсутствует имя | узел локально непригоден для проверок имени |
| `MALFORMED_HEADING` | нарушена форма заголовка | не запускай на этом узле дублирующую проверку формы заголовка |
| `UNCLOSED_QUOTE` | не закрыта кавычка токенизируемого аргумента | не доверяй `Value` ошибочного элемента; остальные узлы анализируй |
| `INVALID_BLOCK_OPEN` | нарушена форма открывающей границы | используй частичную структуру как есть, не перестраивай блок |
| `ORPHAN_BLOCK_CLOSE` | `}` не имеет открытого блока | сохрани boundary-узел и диапазон ошибки |
| `INVALID_BLOCK_CLOSE` | строка закрытия начинается `}`, но содержит лишние символы | не считай её корректным закрытием |
| `UNCLOSED_BLOCK` | открытый блок не закрыт | сохрани диапазон открывающей границы; `Block.Closed() == false` |
| `UNSUPPORTED_TAG_FORM` | известный тег использован в неподдерживаемой inline/block-форме | не выдавай числовой дубль формы |
| `MISSING_SEPARATOR` | у `@matching` отсутствует обязательный `---` | не запускай дубль; дочерние группы могут быть неклассифицированы |
| `MULTIPLE_SEPARATORS` | лишний `---` в `@example`, `@matching` или `@ordering` | не запускай дубль; используй сохранённое неклассифицированное тело |
| `STEP_OUTSIDE_TASK` | `@step` вне активного задания | не создавай собственную ошибку контекста для того же узла |
| `ENDTASK_WITHOUT_TASK` | `@endtask` без открытого задания | та же политика |
| `SPEAKING_CONTEXT` | `@speaking` без допустимого непосредственно предшествующего задания | та же политика |
| `VARIANT_OUTSIDE_VARIANTS` | `@variant` вне `@variants` | та же политика |
| `NESTED_VARIANTS` | вложенный `@variants` | та же политика |
| `CONTENT_BEFORE_VARIANT` | содержательный узел до первой ветви | та же политика для каждого отмеченного узла |

Для каждой локальной ошибки создай отдельную запись `source: parser`, `level: error`, сохрани `Code`, `Message`, `Span` и `RelatedSpan`, если парсер его вернул. Актуальный адаптер обязан вызывать `RelatedSpan()`, но не должен синтезировать связь при `false`.

Локальные ошибки не делают весь разбор `incomplete`: если все стадии завершились, наличие хотя бы одной такой записи даёт статус `completed_with_errors`.

## 15. Ошибки валидатора по стадиям

Все ошибки валидатора имеют `source: validator` и `level: error`. Используй стабильные коды:

| Стадия | Код | Действие |
|---|---|---|
| запуск | `ASSET_INIT_FAILURE` | выведи в консоль и заверши процесс с ненулевым кодом |
| запуск | `DIAGNOSTIC_REGISTRY_FAILURE` | выведи в консоль и заверши до открытия интерфейса |
| запуск | `SERVER_BIND_FAILURE` | выведи в консоль и заверши; не выбирай другой порт |
| запуск | `BROWSER_OPEN_FAILURE` | выведи URL в консоль и продолжи работу сервера |
| сервер | `SERVER_RUNTIME_FAILURE` | выведи в консоль; если сервер остановлен, заверши ненулевым кодом |
| сервер | `TEMPLATE_RENDER_FAILURE`, `HTTP_HANDLER_PANIC` | верни доступную страницу `500`, выведи ошибку в консоль; не создавай файловый отчёт без завершённого результата анализа |
| завершение | `SHUTDOWN_FAILURE` | выведи в консоль и заверши ненулевым кодом после исчерпания таймаута |
| конфигурация | `WORKDIR_NOT_ABSOLUTE`, `WORKDIR_NOT_FOUND`, `WORKDIR_NOT_DIRECTORY`, `WORKDIR_ACCESS_FAILURE`, `WORKDIR_REPARSE_POINT` | покажи ошибку у поля и в фиксированной строке состояния; не запускай сканирование |
| сканирование | `SCAN_ENTRY_FAILURE` | добавь в таблицу ошибок операции и продолжи доступные ветви |
| файл | `FILE_INFO_FAILURE` | свяжи с файлом, если путь известен; при анализе попытайся создать минимальный отчёт |
| файл | `FILE_OPEN_FAILURE` | версия не определена; при анализе создай минимальный отчёт, если возможно |
| парсер | `PARSER_CONTRACT_FAILURE`, `PARSER_UNEXPECTED_ERROR`, `PARSER_PANIC` | минимальный отчёт `incomplete/parsing`; продолжи следующий файл |
| диагностика | `DIAGNOSTIC_EXECUTION_FAILURE` | сохрани уже выданные валидные findings, добавь ошибку с кодом диагностического определения и продолжи |
| диагностика | `DIAGNOSTIC_PANIC` | добавь ошибку, не выводи stack в JSON, продолжи |
| диагностика | `DIAGNOSTIC_RESULT_INVALID` | отбрось только некорректное срабатывание, добавь ошибку и продолжи |
| сериализация | `REPORT_SERIALIZE_FAILURE` | не трогай старый отчёт; покажи ошибку операции и выведи её в консоль |
| запись | `REPORT_PATH_CONFLICT` | не перезаписывай чужой/повреждённый файл по каноническому пути; покажи ошибку операции и консоль |
| запись | `REPORT_TEMP_CREATE_FAILURE`, `REPORT_WRITE_FAILURE`, `REPORT_SYNC_FAILURE`, `REPORT_CLOSE_FAILURE`, `REPORT_REPLACE_FAILURE` | сохрани старый отчёт, удали временный по возможности, покажи ошибку операции и консоль |
| HTTP | `INVALID_REQUEST` | ответ `400`/`405`, доступное сообщение в интерфейсе; не создавай отчёт |
| состояние | `OPERATION_IN_PROGRESS` | отклони второй запуск с `409`; не запускай параллельную операцию |

Ошибки кандидатов отчётов используй как причины отдельной таблицы: `REPORT_READ_FAILURE`, `REPORT_INVALID_JSON`, `REPORT_SCHEMA_UNSUPPORTED`, `REPORT_SCHEMA_INVALID`, `REPORT_SOURCE_MISMATCH`, `REPORT_DUPLICATE`, `REPORT_ORPHAN`.

Любую иную непредусмотренную, но восстановимую ошибку оберни ближайшим стабильным кодом стадии и сохрани исходную ошибку через `%w` во внутреннем Go-значении. Не добавляй в JSON stack trace и не создавай новый публичный код только из-за иной формулировки той же причины.

Если ошибка относится к конкретному сценарию и канонический отчёт можно записать, включи её в отчёт этого сценария. Если ошибка возникла до выбора файла, относится к каталогу/чужому отчёту либо делает запись отчёта невозможной, покажи её в итогах операции; в консоль выводи только ошибки запуска/сервера и случаи, когда требуемый отчёт невозможно создать или заменить.

Не создавай отдельный log-файл. Неперехватываемое завершение процесса операционной системой, включая фатальную нехватку памяти рантайма, находится вне гарантии приложения; не обещай сформировать отчёт после такого завершения.

## 16. Статусы файла и операции

Используй статусы отчёта:

- `completed` — конвейер завершён и нет записей уровня `error`; предупреждения и рекомендации допустимы;
- `completed_with_errors` — все доступные стадии завершены, но присутствует хотя бы одна запись уровня `error`;
- `incomplete` — файл не удалось открыть, парсер не построил `Document` либо контракт парсера не выполнен.

Поле `failed_stage` допускает `opening`, `parsing`, `reporting` либо `null`. Для `completed` и `completed_with_errors` оно всегда `null`. Сбой одной диагностики, после которого runner продолжил остальные функции и сформировал отчёт, даёт `completed_with_errors`, а не `incomplete`.

Отмена операции прекращает постановку новых файлов после завершения текущего. Не прерывай текущий файл через `context` и не оставляй частичный JSON. Для не начатых файлов отчёты не создавай и не заменяй. Отмена является состоянием операции, а не диагностической записью.

## 17. Формат JSON-отчёта

Создай строгие типизированные структуры и JSON Schema `schema/report-v1.schema.json`. Используй `schema_version: 1` как целое число.

Форма верхнего уровня:

```json
{
  "schema_version": 1,
  "source_file": {
    "path": "C:\\Lessons\\lesson.txt",
    "name": "lesson.txt"
  },
  "dsl_version": {
    "status": "determined",
    "raw": "1.1",
    "canonical": "1.1"
  },
  "analysis": {
    "version_mode": "auto",
    "selected_version": null,
    "status": "completed",
    "failed_stage": null,
    "started_at": "2026-09-02T11:00:00+03:00",
    "finished_at": "2026-09-02T11:00:00+03:00",
    "duration_ms": 25,
    "timezone": "Europe/Riga"
  },
  "summary": {
    "total": 0,
    "by_level": {"error": 0, "warning": 0, "recommendation": 0},
    "by_source": {"parser": 0, "diagnostic": 0, "validator": 0},
    "has_errors": false
  },
  "entries": []
}
```

Правила полей:

- `source_file.path` — абсолютный очищенный путь; `name` — basename; это единственные поля идентичности источника;
- при неопределённой версии используй `status: "undefined"`, `raw: null`, `canonical: null`;
- `version_mode` принимает `auto` или `explicit`; при `auto` `selected_version` равен `null`, при `explicit` содержит каноническую версию;
- время записывай по RFC 3339 с числовым смещением;
- `timezone` содержит имя системной зоны, если его удалось определить, иначе `null`;
- `duration_ms` — неотрицательное целое число;
- все три уровня и все три источника присутствуют в счётчиках даже при нуле;
- `has_errors` истинно тогда и только тогда, когда `by_level.error > 0`.

Запись отчёта:

```json
{
  "number": 1,
  "code": "INVALID_UTF8",
  "level": "error",
  "source": "parser",
  "category": null,
  "title": null,
  "message": "вход содержит некорректный UTF-8",
  "description": null,
  "basis": null,
  "location": null,
  "related_location": null,
  "context": null,
  "reference": null,
  "bad_example": null
}
```

Для `source: diagnostic` поля `category`, `title`, `description`, `basis`, `reference`, `bad_example` обязательны и копируются из паспорта. Для `parser` и `validator` они `null`; HTML отображает `Не применяется`. Не придумывай паспорта для технических ошибок.

`location` и `related_location` имеют форму:

```json
{
  "start": {"line": 10, "column": 3},
  "end": {"line": 10, "column": 8},
  "end_exclusive": true
}
```

Сохраняй координаты парсера без преобразования. В HTML показывай привычный включительный конец; для непустого однострочного диапазона вычитай один Unicode-столбец из исключающего конца. Для отсутствующего диапазона показывай `Позиция не определена`.

Контекст имеет форму `{"lines":[{"number":9,"role":"before","text":"..."},{"number":10,"role":"problem","text":"..."},{"number":11,"role":"after","text":"..."}]}`. Показывай только первую проблемную строку и доступные соседние строки.

Строй контекст только из нормализованных `Raw()` готового AST:

- строк объявления — из `Node.Raw()`;
- строк непрозрачных тел — из элементов `ElementBodyLine`;
- закрытия блока — из `Block.CloseSpan()` со значением `}`;
- директиву версии используй только через данные `Document`, не восстанавливай её формат догадками.

Если нужная строка не представлена готовым AST либо `Document` отсутствует, сохраняй `context: null`. Не открывай файл повторно ради контекста.

Перед нумерацией отсортируй записи по началу основного диапазона. Записи без диапазона размести после записей с диапазоном. При совпадении используй приоритет источника `parser`, `diagnostic`, `validator`, затем порядок определения и порядок выдачи. Назначь `number` с единицы; он не меняется при сортировке таблицы в браузере.

## 18. Атомарная запись отчёта

Сначала полностью сформируй и сериализуй JSON в памяти с отступом в два пробела и завершающим переводом строки. Затем:

1. проверь существующий канонический путь;
2. разреши замену только если файл отсутствует либо является валидным отчётом того же сценария;
3. создай временный файл в том же каталоге;
4. запиши все байты, выполни `Sync`, проверь `Close`;
5. замени целевой файл одной файловой операцией;
6. при любой ошибке сохрани старый отчёт и удали временный по возможности.

На Windows реализуй замену существующего файла стандартными средствами через `MoveFileExW` с `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`; не добавляй `golang.org/x/sys`. Для тестов на иных ОС предоставь эквивалент под build tags с `os.Rename`.

Не перезаписывай повреждённый, чужой или неподдерживаемый JSON, случайно занявший каноническое имя. Верни `REPORT_PATH_CONFLICT`. Не выбирай альтернативное имя, потому что формат имени отчёта фиксирован.

## 19. HTTP-сервер и состояние

Слушай только `127.0.0.1:8580`. Не привязывайся к `0.0.0.0`, IPv6 wildcard и внешнему интерфейсу. После запуска попробуй открыть системный браузер; неудача открытия не останавливает сервер.

Поддержи один активный рабочий каталог и не более одной операции анализа. Храни состояние в памяти процесса, защищая его обычным mutex только от одновременных HTTP-запросов; сами файлы обрабатывай последовательно.

Используй маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/` | стартовая страница |
| `POST` | `/workspace` | проверка пути/версии, сканирование и redirect на список |
| `GET` | `/files` | таблица сценариев и отклонённых отчётов |
| `POST` | `/analysis/file` | запуск одного файла по непрозрачному ID текущего сканирования |
| `POST` | `/analysis/all` | запуск набора по правилам выбранной версии |
| `GET` | `/progress` | страница текущей/завершённой операции |
| `GET` | `/api/progress` | компактное JSON-состояние для polling |
| `POST` | `/analysis/cancel` | запрос мягкой отмены |
| `GET` | `/report/{id}` | серверная страница активного отчёта |
| `POST` | `/shutdown` | корректная остановка сервера |
| `GET` | `/assets/*` | только встроенные CSS/JS |

Не принимай абсолютный файловый путь в URL или action-форме. Назначай найденным сценариям и отчётам непрозрачные ID, действительные только для текущего сканирования, и разрешай их через серверное состояние. После завершения анализа кнопка `Вернуться к списку` выполняет новое сканирование.

Изменяющие маршруты обслуживай только методом `POST`. CSRF-токен не требуется. Проверяй `Host` и принимай `127.0.0.1:8580` и `localhost:8580`. Установи таймауты HTTP-сервера, ограничь размер form body и выставь `Content-Type`, `X-Content-Type-Options: nosniff` и CSP, разрешающую ресурсы только с `self`.

Кнопка `Завершить работу` вызывает `Server.Shutdown` с конечным таймаутом. Закрытие вкладки браузера сервер не завершает.

## 20. Пользовательские страницы

### 20.1. Стартовая страница

Покажи абсолютный путь, `select` версии, кнопку продолжения и кнопку завершения. Ошибки пути свяжи с полем через `aria-describedby`. При ошибке оставь введённые значения.

### 20.2. Список сценариев

Покажи выбранный каталог и режим версии, сводку сканирования, кнопку `Проанализировать все`, таблицу файлов и отдельную таблицу отклонённых/конфликтных отчётов. Для файла предоставь `Проанализировать` и, только при наличии активного валидного отчёта, `Открыть отчёт`.

Не добавляй действие `Открыть сценарий`.

### 20.3. Прогресс и итог операции

Покажи текущий файл и счётчики: всего выбрано, обработано, `completed`, `completed_with_errors`, `incomplete`, исключено выбором версии и осталось. Обновляй визуальные значения polling-запросом. Live-region обновляй только при переходе к следующему файлу, ошибке, отмене и завершении, чтобы не перегружать скринридер.

После завершения оставайся на итогах. Не перенаправляй автоматически. Кнопка возврата запускает новое сканирование.

### 20.4. Страница отчёта

Покажи метаданные файла, версию DSL, статус, время, длительность, сводку и одну таблицу записей. Добавь независимые фильтры по уровню, источнику и категории; каждый имеет значение `Все`.

Используй порядок основных столбцов: номер, код, уровень, источник, категория, название, сообщение/описание, основание, позиция, контекст, эталон, неудачный пример. Столбец `Источник` всегда находится после уровня и перед категорией. Начальная сортировка — номер по возрастанию.

Добавь сортировку по номеру, коду, уровню, источнику, категории и местоположению с выбором направления. Отсутствующие код, категория или позиция всегда идут после заполненных независимо от направления. При равной строке и позиции номер записи всегда возрастает.

Не делай пагинацию. Длинный контекст, эталон и неудачный пример помести в доступные `details/summary`; сохраняй переносы. После кнопки `Применить` оставляй фокус на кнопке и объявляй количество видимых записей через фиксированную строку состояния.

Перенеси из `STM.html` визуальную систему, а не предметную логику:

- тёмный фон `#0f1411`, поверхности `#171d19` и `#1d2520`;

- нативные button/input/select/details/table и минимальная высота управляющих элементов `2.5rem`.

## 22. Тестирование

Пиши тесты до production-кода. Используй только `testing`, `httptest` и встроенные средства Go.

Обязательно покрой:

1. подключение точного модуля парсера и запрет прямых импортов;

Не задавай искусственный процент покрытия. Каждый контракт, ветвление ошибки и исправленный дефект обязан иметь тест.

## 23. Требования к коду и проверке

Используй Go `1.26`, идиоматический код, `gofmt`, направленный граф пакетов и русские doc-комментарии. Выполняй актуальный `AGENTS.md` проекта валидатора в том месте, куда он будет перемещён. Не копируй правила из репозитория парсера как правила приложения.

Документируй по-русски каждый пакет, тип, функцию, метод, константу, переменную уровня пакета и нетривиальное поле, включая неэкспортируемые идентификаторы. Для полуоткрытых диапазонов явно указывай исключающий конец, для булевых результатов — смысл обоих значений.

Создай `README.md` с установкой закрытой зависимости, сборкой, запуском, пользовательским потоком и командами проверки; `docs/architecture.md` с графом пакетов и стадиями; `docs/report-format.md` со schema v1; `docs/adding-diagnostics.md` с правилами категории, версии, отсутствия дублей и тестирования. Документация обязана описывать только фактически реализованный код.

Не используй `unsafe`, reflection, нетипизированные контейнеры для структурированных данных, mutable globals и `panic` как управление потоком. Любое состояние операции должно принадлежать одному запуску.

Перед завершением выполни из корня проекта:

```text

go test -race ./...
go vet ./...
go list ./...
go list -m all
GOOS=windows GOARCH=amd64 go build -trimpath -o build/validator.exe ./cmd/validator
```

`go list -m all` должен содержать только модуль валидатора и `github.com/verdoga/dslparser` с его закреплённой псевдоверсией. Не объявляй работу завершённой при неуспешной команде.

## 24. Критерии приёмки

Результат принят, только если одновременно выполнено следующее:

- приложение собирается в один Windows `amd64` `.exe` и не требует frontend-файлов рядом;
- парсер подключён как внешний модуль по закреплённому коммиту, без копии исходников;
- версия файла определяется исключительно результатом парсера;
- при любом fatal-коде создаётся минимальный отчёт, если файловая система это позволяет, и ни одна библиотечная диагностика не запускается;
- при local-кодах сохраняется одна parser-запись на логическую ошибку и продолжаются независимые диагностики;
- parser/diagnostic/validator никогда не смешиваются в одном значении `source`;
- `Diagnostics/` находится в корне и не импортирует парсер;
- одна функция регистрируется для одной, нескольких либо всех версий без копирования кода;
- API валидатора достаточен для всех 95 текущих примеров без `SourceView` и доступа диагностик к файлу;
- отчёты валидны по schema v1, полностью формируются в памяти и заменяются crash-safe операцией;
- повреждённые, конфликтные и orphan-отчёты не теряются и видны отдельно;
- все файлы обрабатываются последовательно, отмена не обрывает текущий файл;
- интерфейс содержит выбор auto/1.1, версию в таблице файлов, прогресс, отчёт, фильтры и сортировку, но не содержит открытия сценария;
- ошибки, которые можно связать со сценарием, попадают в его отчёт; отдельный технический log-файл не создаётся;
- стартовые и неперсистируемые ошибки явно видны в консоли;
- все проверки раздела 23 проходят.

В итоговом сообщении разработчик должен указать закреплённую версию зависимости, перечислить созданные пакеты, сообщить результаты команд проверки и отдельно назвать ограничения, если какая-либо внешняя или файловая блокировка не позволила выполнить критерий. Не подменяй невыполненную проверку предположением.

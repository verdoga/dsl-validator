# dsl-validator

Консольное приложение на Go для проверки JSON-результатов разбора DSL. Принимает формат результата `1.0`, сейчас поддерживает DSL `1.2`. Исходный DSL повторно не разбирается; зависимости от Go-модуля `dsl-parser` нет.

**Текущее состояние:** каталог `checkers.RegistrationCheckers()` пуст. Справка доступна, но обычный запуск после успешного поиска файлов сообщает `Ошибка: диагностики не зарегистрированы` и возвращает код `1`, не открывая и не изменяя JSON. Для выполнения проверок нужно добавить реальные диагностики в `checkers`.

## Требования и сборка

Нужен Go 1.25.1 или новее. Используется только стандартная библиотека.

Из корня репозитория:

```sh
mkdir -p bin
go build -o bin/dsl-validator .
```

Версия обычной сборки — `dev`. Сборка выпуска `1.0.0`:

```sh
go build -ldflags '-X main.version=1.0.0' -o bin/dsl-validator .
```

В Windows исполняемый файл можно собрать командой `go build -o bin/dsl-validator.exe .`.

## Запуск

```sh
./bin/dsl-validator --help
./bin/dsl-validator ./result.json
./bin/dsl-validator --depth 0 ./results
./bin/dsl-validator --depth 2 ./results
```

Принимается один обычный файл `.json` или каталог. Регистр расширения не важен. Без `--depth` глубина обхода не ограничена; `0` разрешает только исходный каталог. Для отдельного файла глубина игнорируется. Флаги указываются до пути; `--` завершает разбор флагов. Символические ссылки в исходном пути запрещены, ссылки внутри обхода пропускаются. JSONC не является входным форматом.

После регистрации диагностик обработка выполняется последовательно:

1. Приложение находит и сортирует пути JSON, создаёт реестр проверок.
2. Для каждого файла читает JSON, проверяет поддержку DSL-версии, выбирает подходящие диагностики и проверяет целостность модели.
3. Добавляет запись текущего запуска и выполняет выбранные проверки в порядке номеров V-кодов.
4. При успехе сохраняет дополненный JSON по исходному пути и печатает отчёт.

Сохраняются история запусков, прежние диагностики и неизвестные поля JSON. Новые записи дополняют историю; флаги `hasErrors` пересчитываются по всем диагностикам уровня `error`. Запись выполняется через временный файл и резерв исходного JSON. При отказе установки выполняется восстановление; если оно невозможно, сообщение об ошибке содержит путь к резерву.

Первый технический отказ прекращает обработку следующих файлов. При ошибке проверки текущий JSON не сохраняется; уже сохранённые предыдущие файлы не откатываются. Штатные отчёты идут в `stdout`, сообщения о технических отказах — в `stderr`.

| Код завершения | Значение |
| --- | --- |
| `0` | Справка или успешная обработка, включая любые срабатывания `error`, `warning`, `recommendation`. |
| `1` | Технический отказ, пустой реестр, неподдерживаемая DSL-версия или отсутствие подходящих проверок. |
| `2` | Неверные аргументы или непригодный исходный путь. |

## Пакеты

| Путь | Назначение |
| --- | --- |
| `main.go` | Аргументы, версия сборки и завершение процесса. |
| `app` | Последовательная обработка файлов и история запусков. |
| `console`, `discovery` | Параметры, проверка путей и поиск JSON. |
| `model` | Структуры JSON-результата. |
| `diagnostics` | Типы диагностик, реестр, интерфейсы чтения строк и накопления срабатываний. |
| `dsl-versions` | Поддерживаемые DSL-версии и их числовое сравнение. |
| `checkers` | Каталог регистраций конкретных проверок. |
| `validator` | Допуск модели, выполнение проверок, ссылки и флаги ошибок. |
| `storage` | Чтение JSON и сохранение дополнений с сохранением неизвестных полей. |
| `reporter` | Отчёты по файлам и общий итог. |

`model` использует типы из `diagnostics`; обратного импорта нет. Контракты API описаны в комментариях к объявлениям. Проверки работают через `diagnostics.Lines` и `diagnostics.Findings`, без прямого доступа к изменяемой модели. Непустая конкретизация срабатывания добавляется к нормативному сообщению после `\nконкретизация: `.

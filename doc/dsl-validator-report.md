# dsl-validator: отчёт об архитектуре

Подготовлены контракты одного консольного приложения на Go 1.25. Реализации функций и алгоритмов отсутствуют. Парсер, грамматики, сервер, интерфейс браузера, многопоточность и конкретные V-диагностики в приложение не входят.

**Пустой реестр — обрабатываемая ошибка запуска с кодом 1.** Сначала выполняется обнаружение файлов, затем подготовка реестра. Если в реестре нет диагностик, приложение выводит ошибку и завершается: найденные JSON не открываются, `validator.Run` не вызывается, `processing` и остальные данные файлов не изменяются. Наличие функций регистрации в карте недостаточно: проверяется именно `Registry.Len()` после их выполнения.

**Уточнение по полученным ответам.** Первый технический сбой прекращает весь конвейер. Сбой `Check` выводится в `stderr` с фактическим V-кодом диагностики; её накопленные срабатывания в модель не переносятся. Любое количество обычных срабатываний `error`, `warning` и `recommendation` совместимо с успешным завершением и кодом 0.

**Поддержка версий DSL.** Добавлен отдельный пакет `dsl-versions` с каталогом, в котором сейчас только `1.2`. Реестр выбирает диагностики по версии каждого документа. Допуск выполняется в `validator.Prepare` сразу после чтения JSON и до любых изменений модели; неподдерживаемая версия прекращает конвейер с сообщением в `stderr` и кодом 1, без добавления `processing`.

Основание проекта: приложенные `AGENTS.md`, `Contract.jsonc`, `model.go`, `diagnostics.go`, контракты остальных пакетов, необходимые положения `DSL v1.2(1).md` и код [verdoga/dsl-parser](https://github.com/verdoga/dsl-parser/tree/cc52a1434b9c47a9c52b851e63673734fcef1a32). Для сверки использован коммит `cc52a1434b9c47a9c52b851e63673734fcef1a32`. Репозиторий доступен; изучены реальные функции подготовки модели, присоединения диагностик, формирования ссылок, проверки целостности, обработки путей и сохранения JSON. В его `go.mod` указана версия 1.25.1. Правила организации взяты из приложенного `AGENTS.md`; файла с таким именем в корне проверенного репозитория нет.

## 2. Ключевые архитектурные решения

**Порядок работы.** После проверки параметров приложение обнаруживает файлы, создаёт реестр и проверяет его непустоту. Только после этого создаётся отчётчик и начинается цикл файлов. Для каждого файла: единственный `storage.Open` → `validator.Prepare` → новая запись `processing` → `validator.Run` с полученной выборкой → завершение измерения → `storage.Save` → `reporter.Record`. Первый технический отказ прекращает дальнейшую обработку. При ошибке `Check` оставшиеся проверки не запускаются, следующие файлы не открываются, текущий JSON не сохраняется. После начала файлового цикла итог выводится один раз, в том числе при досрочной остановке; он охватывает только фактически начатые попытки обработки.

**Место определения версии.** `Prepare` берёт значение из уже разобранного `document.dslVersion` и передаёт его в `Registry.ForVersion`. Повторного чтения JSON, разбора `raw` или вычисления версии по элементам нет. Сначала проверяется поддержка версии и наличие подходящих диагностик, затем — полная целостность через `CheckModel`. Только после успешного `Prepare` приложение добавляет `processing`. `Run` получает эту же модель и неизменённую выборку; между подготовкой и запуском app вправе добавить только текущий `processing`. Входной `CheckModel` повторно не вызывается; итоговый контроль перед применением результатов сохраняется.

Storage уже сохраняет неизвестное либо отсутствующее значение DSL-версии без подмены: это допустимый результат работы парсера. Поэтому его контракт менять не требуется. Его задача — распознать и прочитать JSON-контракт; каталог поддерживаемых DSL и отбор проверок относятся к валидации. Отказ версии происходит до копирования строк, накопителей, `Check` и изменения даже модели в памяти. Ошибка содержит фактическую версию и список поддерживаемых; reporter добавляет путь файла и выводит её в `stderr`. `Save` не вызывается, следующий файл не открывается, итоговый код — 1. Ранее сохранённые файлы остаются сохранёнными.

**Каталог версий.** Путь пакета — `dsl-versions`, корректный идентификатор Go — `dslversions`: дефис в `package` недопустим. Сейчас `Supported()` возвращает копию списка только с `V1_2`. Поддержка новой версии добавляется явно в этом пакете, независимо от регистрационных правил диагностик. `Parse` проверяет запись, а `RequireSupported` дополнительно проверяет каталог. Версии сравниваются по числовым компонентам, поэтому `1.10` новее `1.2`. Значение `document.dslVersion` не смешивается с `formatVersion` JSON-контракта или версией исполняемого инструмента.

**Применимость диагностик.** В `Definition` добавлено обязательное `Versions` типа `VersionRule`. Оно задаёт одно из четырёх правил; границы включительны:

| Режим | Поле `Version` | Какие поддерживаемые версии выбираются |
|---|---|---|
| `VersionExact` | `1.2` | Только `1.2`. |
| `VersionAll` | Пустое | Все версии из каталога приложения. |
| `VersionFrom` | `1.2` | `1.2` и более новые. |
| `VersionThrough` | `1.2` | `1.2` и более старые. |

Нулевой режим запрещён; для трёх режимов с границей требуется каноническая версия, для `VersionAll` граница запрещена. Граница может ещё не поддерживаться приложением: например, правило «начиная с `1.1`» применимо к поддерживаемой `1.2`. Однако никакое правило не разрешает обработку версии вне каталога. Прежняя уникальность V-кода во всём реестре сохраняется: одна диагностика имеет одно правило и одну функцию `Check`.

`Registry.ForVersion` заменяет неограниченную выборку `All`: проверяет поддержку версии и возвращает копию подходящих определений в порядке V-кодов. Для каждого файла выборка строится заново; результаты первого файла не задают версию остальных. Сам `Check` остаётся автономным и получает прежние `Lines` и `Findings`, без доступа к метаданным документа. Версию проверяемого документа определяет конвейер.

**Отсутствие работы.** Глобально пустой реестр по-прежнему останавливает приложение после обнаружения, до открытия любого JSON. Если реестр непустой, но для поддерживаемой версии конкретного документа выборка пуста, `ForVersion` возвращает пустой срез, а `Prepare` формирует ошибку с версией. Такой файл уже прочитан для определения версии, но модель, `processing` и JSON не меняются. Это также остановка всего конвейера с кодом 1.

**Регистрация без циклов.** `app` передаёт `checkers.RegistrationCheckers()` в `diagnostics.NewRegistry`. Сам конструктор последовательно вызывает функции карты и принимает определения через `Registry.Register`. Глобального предзаполненного реестра, `init` и скрытой саморегистрации нет. Единственный литерал каталога регистраций принадлежит `checkers`; созданный реестр хранит описания в срезе. Повторный код, неверное описание или ошибка регистрации прекращают подготовку; частичный реестр не публикуется. После конструктора добавлять определения нельзя. Исполнение идёт по номеру V-кода независимо от порядка обхода карты.

**Полный перенос модели.** `model.go` совпадает с приложенным контрактом, включая типы, поля и JSON-теги. Объявления модели также сверены с [моделью в репозитории](https://github.com/verdoga/dsl-parser/blob/cc52a1434b9c47a9c52b851e63673734fcef1a32/model/result.go). `Code`, `Severity` и `Scope` остаются в `diagnostics`, потому что существующая модель ссылается на них. Удалены именно определения конкретных диагностик парсера и их константы; перечисления формата сохраняются.

**Фатальность.** Подтверждено: в реестре и API проверок нет признака фатальности. Поле `model.Diagnostic.Fatal` остаётся частью переносимой модели и прежнего JSON-контракта. Исторические значения сохраняются; новые записи валидатора всегда получают `false`. Остановка из-за технического сбоя не создаёт фатальную диагностику и не меняет это правило.

**Ограниченный доступ проверки.** `Check` получает только `diagnostics.Lines` и `diagnostics.Findings`. Ей доступны `raw`, тип, окончание строки, глубина, номер родителя и все содержательные поля элементов. Доступа к `Document`, `Processing`, `Diagnostics`, `HasErrors` и `ErrorIDs` нет. Флаги и ссылки исключены даже из приватной проекции строк. Указатели, срезы и карты наружу не выдаются. Обход вперёд и назад выполняется через номера `1..Len`; курсор и отдельный пакет обхода не нужны.

Интерфейсы здесь необходимы именно для ограничения доступа. Отдельные интерфейсы для реестра, файлового хранилища, приложения и отчётчика не вводятся. В `diagnostics` не импортируется `model`: типы строк возвращаются их существующими строковыми значениями, координаты принимаются числами. Преобразование в существующие `model.Position` и `model.Location` выполняет валидатор. Копий этих структур в API диагностик нет.

**Срабатывание не является записью ошибки.** Проверка передаёт диапазон, при необходимости конкретное сообщение и связанные места. Область, код и уровень берутся из зарегистрированного определения. ID, Source и обратные ссылки назначает только валидатор. Для документа без позиции предусмотрены четыре нуля; это не фиктивная строка 0 в модели. Для элемента требуется точное совпадение с его диапазоном; произвольную часть строки следует диагностировать областью `line`.

**Изоляция накопления.** У каждого `Check` собственный накопитель. Первая ошибка API сохраняется внутри него и запрещает дальнейшее накопление; проверка обязана немедленно вернуть её. Даже проигнорированная ошибка не позволит перенести частичные срабатывания. При сбое накопитель закрывается, все срабатывания этой проверки отбрасываются, а `validator.Run` возвращает одну `*CheckFailure` с её V-кодом. Списка технических отказов больше нет, поскольку следующая проверка не выполняется.

Сохраняется ранее заложенное правило применения результатов одного файла: принятые срабатывания находятся в отдельной копии изменяемых частей, которая заменяет модель только после успеха всех проверок и контроля инвариантов. Поэтому при техническом сбое текущий JSON остаётся неизменным целиком, включая `processing`; промежуточные результаты предыдущих проверок этого же файла также не записываются. Результаты ранее завершённых файлов уже сохранены и не откатываются.

**Передача технической ошибки.** `CheckFailure` реализует обычный `error` и `Unwrap`; её сообщение содержит фактический код, например `сбой диагностики V001: <причина>`. Reporter направляет сообщение с путём JSON в `stderr`, а app завершает конвейер с кодом 1 без повторной печати причины. Сам технический отказ в JSON не записывается. Обычные отказы возвращаются через `error`; непредвиденный `panic` внутри вызова `Check` перехватывается только на этой границе и превращается в такой же технический отказ с остановкой. Возобновления работы после него нет.

**История и ссылки.** Каждый фактически начатый запуск над принятой моделью добавляет свой `processing.id`. Новые диагностические ID выбираются с учётом всех прежних записей. `diagnostics.source` ссылается на конкретный запуск, а не на строку `validator`. Исторические записи и их ID сохраняются. Новые `element`-диагностики получают обратные ссылки независимо от уровня; `hasErrors` устанавливается только для уровня `error`. Связанные места, родительские и дочерние строки не наследуют ошибку. Правила сверены с [реализацией парсера](https://github.com/verdoga/dsl-parser/blob/cc52a1434b9c47a9c52b851e63673734fcef1a32/parser/diagnostics.go).

Целостность ID, ссылок и флагов — исключительно ответственность валидатора. Диагностики не видят `errorIds`/`hasErrors`, не знают об их обновлении и не участвуют в нём. Это подтверждённая граница API. Новая запись `processing` попадает в файл только вместе с успешно сохранённым результатом; после отказа `Check` созданная в памяти запись не сохраняется.

**Граница проверок целостности.** Storage распознаёт JSON и обязательную форму контракта. Validator сначала проверяет допуск по версии, затем номера, координаты, ID, ссылки, перечисления и производные флаги. Это проверка пригодности и сохранности модели, а не повторный разбор DSL и не набор скрытых диагностик. Уже записанные ошибки парсера сами по себе не запрещают запуск при поддерживаемой версии и пригодной модели. Неоднозначные или ошибочные элементы остаются такими, какими их сохранил парсер.

**Сохранение того же JSON.** Назначение записи берётся из пути обнаруженного JSON, а не из `document.filePath`: последний описывает исходный DSL. Storage открывает и закрывает файловые дескрипторы внутри операций. Наружу передаётся только `Snapshot` исходных байтов, необходимый для сохранения неизвестных полей и контроля замены. Неизвестные поля игнорируются при анализе, но сохраняются при записи на любом уровне.

Обновляются новые суффиксы `processing` и `diagnostics`, `document.hasErrors`, `lines[].hasErrors` и дополненные `elements[].errorIds`. Текст, структура, метаданные и старые диагностические записи не переписываются. Полная новая версия сначала готовится во временном файле, затем устанавливается с возможностью восстановления прежней. Отдельные постоянные отчётные JSON не создаются.

**Отчёт и длительность.** Три уровня выводятся как «ошибки», «проблемы», «рекомендации»; машинные значения остаются `error`, `warning`, `recommendation`. Ни один уровень срабатывания не влияет на код завершения: нахождение проблем — штатная работа валидатора. Отчёт считает только Source текущего запуска, чтобы повторный запуск не суммировал всю историю. При этом `document.hasErrors` продолжает отражать все диагностики модели. Факт сохранения и технический отказ показываются отдельно. Штатные отчёты и итог идут в `stdout`, технический отказ — в `stderr` с причиной и V-кодом, если сбой относится к `Check`. Время включает чтение, закрытие входа, подготовку по версии, контроль модели и проверки; сохранение и печать в него не входят, как в [app парсера](https://github.com/verdoga/dsl-parser/blob/cc52a1434b9c47a9c52b851e63673734fcef1a32/app/runner.go).

При отказе `Prepare` новый `ProcessingID` отсутствует, в отчёт передаётся `Result=nil`, новые срабатывания не учитываются, а длительность попытки существует только в консольном отчёте. Уже имеющиеся `FileReport.Err`, `ProcessingID` и `Updated` описывают этот случай; менять `reporter` не требуется. Версионный отказ относится к подготовке валидатора и не получает вымышленный V-код диагностики.

| Ситуация | Поведение | Exit code |
|---|---|---:|
| Ошибка аргументов или исходного пути | До обнаружения/обработки файлов | 2 |
| Запрос справки | Только справка | 0 |
| Реестр пуст после обнаружения файлов | Ошибка; JSON не открываются и не меняются | 1 |
| Ошибка регистрации | Ошибка; JSON не открываются | 1 |
| Версия DSL отсутствует, некорректна или не поддерживается | Причина и поддерживаемые версии в `stderr`; модель и JSON не меняются, конвейер останавливается | 1 |
| Версия поддерживается, но подходящих диагностик нет | Ошибка с версией в `stderr`; `processing` не создаётся, JSON не меняется, конвейер останавливается | 1 |
| Реестр непустой, файлов нет, обход успешен | Итог с нулями | 0 |
| Найдены новые диагностики `error` | Штатный результат; результаты сохраняются, обработка продолжается | 0 |
| Найдены только `warning`/`recommendation` | Результаты сохраняются | 0 |
| Первый технический сбой `Check` | `stderr` с V-кодом; результаты сбойной проверки отбрасываются; текущий JSON не сохраняется; весь конвейер останавливается | 1 |
| Техническая ошибка чтения, целостности модели, записи, вывода или обхода | Причина в `stderr`; дальнейшая обработка прекращается | 1 |

|---|---|
| `dslversions`, `console` | Нет |

| `model`, `checkers` | `diagnostics` |
| `discovery` | `console` |
| `storage` | `console`, `model` |
| `validator` | `diagnostics`, `dslversions`, `model` |

## 3. Допущения и подтверждённые правила

1. Вход — строгий JSON контракта 1.0, а `Contract.jsonc` служит документацией. JSONC на входе и автоматическая миграция формата не поддерживаются. Принадлежность к DSL определяется структурой: отдельной сигнатуры формата в текущем контракте нет.
2. Нулевой реестр трактуется строго по уточнению: обнаружение выполняется, затем ошибка и код 1; чтение содержимого файлов не начинается. Это заданное поведение, а не вопрос для согласования.
3. Подтверждено: историческое `fatal` сохраняется, новые записи валидатора имеют `false`. Только валидатор дополняет `errorIds` и пересчитывает `hasErrors`; диагностики этих полей не видят.
4. Повторная валидация добавляет историю и новые срабатывания. Старые диагностические записи, даже с тем же кодом и диапазоном, не удаляются: контракт прямо предусматривает накопление запусков.
5. Подтверждено: технический сбой `Check` выводится только в консоль, в `stderr` с V-кодом; первый сбой останавливает весь конвейер с кодом 1. Его частичные срабатывания не переносятся. Сохранено правило отказа от записи текущего файла целиком; уже сохранённые файлы не откатываются.
6. Подтверждено: `error`, `warning` и `recommendation` являются штатными результатами и оставляют код 0. Код 1 относится к техническим отказам выполнения/подготовки валидатора и его диагностик, включая пустой реестр. Прежний код 2 для неверных параметров или исходного пути сохраняется.
7. Проверки — доверенный код того же приложения, обязанный соблюдать `AGENTS.md`: без `unsafe`, отражения, I/O, фоновых задач и общего изменяемого состояния. Закрытое API защищает модель при обычном использовании Go; изоляция произвольного вредоносного кода отдельным процессом не проектируется. Обычные ошибки передаются через `error`; локальное преобразование неожиданного `panic` в сбой служит только для сообщения с V-кодом и остановки.
8. Временный файл и резерв при замене допустимы; после успеха они удаляются. При отказе восстановления пригодный резерв сохраняется с указанием пути в ошибке. Переносимая стандартная библиотека не даёт обещания атомарности последовательности переименований при аварийном отключении ОС. Одновременное внешнее изменение того же JSON не является поддерживаемым режимом; обнаруженное изменение до записи приводит к отказу.
9. Выбрано единое имя пакета `checkers`, использованное в основном описании задачи. Отдельный пакет `checker` не требуется. Карта регистраций пока пуста; конкретные диагностики не добавлены.
10. Источник версии — `document.dslVersion`, уже заполненное парсером. `null`, пустая строка, неверная запись и значение вне каталога запрещают обработку; автоматического выбора `1.2`, повторного разбора строк и изменения версии нет. Сейчас поддерживается только `1.2`.
11. Для сравнения будущих версий принято каноническое `major.minor`: две неотрицательные десятичные компоненты `uint64` без лишних ведущих нулей. Префиксы, пробелы, третья компонента и суффиксы не принимаются. Это допущение о нумерации будущих DSL, не расширение текущей спецификации `1.2`.
12. Отсутствие диагностик для поддерживаемой версии принято ошибкой подготовки с кодом 1, по аналогии с пустым реестром. Неподдерживаемая версия тоже прекращает весь конвейер согласно ранее подтверждённому правилу первого технического отказа; перехода к следующему файлу нет.

## 4. Вопросы, требующие уточнения

Все четыре ранее поставленных вопроса получили ответы и закрыты:

| Вопрос | Принятое решение |
|---|---|
| Технический сбой `Check` | Только `stderr`, фактический V-код, остановка всего конвейера, код 1; срабатывания сбойной проверки отбрасываются. |
| Историческое `fatal` | Сохраняется; валидатор пишет `false`. |
| `errorIds` и `hasErrors` | Полностью ведутся валидатором; недоступны диагностикам. |
| Влияние уровней на exit code | Все три уровня, включая `error`, являются штатным результатом и не дают код 1. |

Дополнительных уточнений, блокирующих эти правки, нет. Форма будущих версий и отказ при пустой выборке по версии явно зафиксированы в допущениях. Правило глобально пустого реестра остаётся закрытым: код 1 после обнаружения и до открытия JSON.

## Проверка результата

Проверены единственность `package` в каждом файле пакета, метки файлов, отсутствие тел функций, табуляция, комментарии объявлений и согласованность межпакетных типов. Проверены направленность зависимостей и отсутствие циклов. Каждый обозначенный будущий файл укладывается в 300 строк. Перенесённый `model.go` совпадает с приложением, его объявления — с проверенной моделью репозитория.

После уточнений согласованы возврат единственной ошибки `Check`, отсутствие списка продолжающихся сбоев, остановка последующих проверок и файлов, маршрутизация технических сообщений в `stderr` и независимость кода завершения от всех трёх уровней срабатываний.

При добавлении версий изменены только `diagnostics.go`, `validator.go`, `app.go` и этот отчёт; добавлен `dsl-versions.go`. Файлы `main.go`, `console.go`, `discovery.go`, `model.go`, `checkers.go`, `storage.go`, `reporter.go` сохранены побайтово, что проверено сравнением SHA-256. Архив пересобран из папки пакетов и отчёта; объединённый файл в него не включён и заново не создавался.

Согласованы четыре режима применимости, включительность границ, числовое сравнение и независимость каталога поддерживаемых версий от диапазонов регистраций. Проверены порядок `Open` → `Prepare` → `processing`, отсутствие изменений модели при отказе версии, отдельная выборка для каждого документа и сохранение остановки до чтения при глобально пустом реестре.

Это псевдокод в запрошенном формате: метки `file` намеренно не являются синтаксисом компилируемого Go-файла. `gofmt`, сборка и `go test` к исходным контрактам не применялись; запуск приложения и алгоритмы не реализованы. Эти проверки потребуются при последующей реализации.

# PLAN.md — реализация `dsl-validator`

## 1. Назначение плана

Выполни этот план последовательно и доведи репозиторий от исходного состояния до компилируемого локального приложения `dsl-validator`, соответствующего `TZ.md`. Не реализуй ни одной предметной диагностики. Итоговая production-библиотека `Diagnostics/` должна быть пустой, валидной и готовой к последующему добавлению диагностик через зафиксированный контракт регистрации и вызова.

План разбит на небольшие задачи. Задачи с пометкой **TEST** добавляют только тесты, fixtures, golden-файлы или тестовые утилиты. Следующая за ними задача **CODE** добавляет production-код, необходимый для прохождения этих тестов. Не объединяй такую пару в одну задачу и не пиши production-код в задаче **TEST**.

## 2. Обязательный порядок источников

Перед началом прочитай целиком актуальный `AGENTS.md`, затем `TZ.md`. Обращайся к `DSL v1.1.md`, `Diagnostics.md` и `STM.html` только в пределах роли, установленной разделом 1 `TZ.md`.

Применяй источники в таком порядке:

1. `AGENTS.md` в области изменяемого файла — правила выполнения работы в репозитории;
2. `TZ.md` — требования к валидатору и зафиксированные архитектурные решения;
3. фактический публичный API `github.com/verdoga/dslparser` на коммите `8486082e285e179c3e506167b69f5b94b981b30c`;
4. `DSL v1.1.md` — предметные правила, нужные только для fixtures и проверки достаточности API;
5. `Diagnostics.md` — примерный каталог из 95 записей, а не перечень диагностик для реализации;
6. `STM.html` — только визуальная система и accessibility-приёмы.

Если `AGENTS.md` противоречит `TZ.md` в предметной архитектуре или составе результата, остановись и опиши точное противоречие. Не выбирай трактовку молча.

## 3. Непререкаемые правила выполнения

1. Выполняй только одну задачу плана за раз и не начинай следующую до выполнения критерия готовности текущей.
2. Сохраняй существующий module path, если в репозитории уже есть `go.mod`. Если `go.mod` отсутствует, инициализируй module path `dsl-validator`.
3. Не изменяй `dslparser`, `DSL v1.1.md`, `Diagnostics.md`, `STM.html` и `TZ.md`.
4. Не реализуй production-определения диагностик, категории диагностик или числовые коды из `Diagnostics.md`. Для тестов используй только определения с кодами вида `TEST_*` внутри `_test.go` или `testdata`.
5. Не импортируй `github.com/verdoga/dslparser` нигде, кроме `internal/parseradapter`.
6. Не создавай интерфейс-заглушку, локальную копию AST, временный парсер, `replace`, vendor-копию или fallback вместо недоступного `dslparser`.
7. Не извлекай `@dsl-version` самостоятельно ни регулярным выражением, ни чтением первой строки, ни строковым поиском.
8. Не добавляй сторонние зависимости. Единственная внешняя зависимость production-кода и тестов — закреплённый `dslparser`.
9. Не копируй из репозитория парсера его `plan.md`, `tz.md`, `DSL v1.1.md`, `AGENTS.md` и любые другие Markdown-файлы. Подключай пакет только через Go Modules. Файлы, которые Go хранит вне проекта в module cache, не копируй, не встраивай и не учитывай как часть валидатора.
10. Встраивай только явные шаблоны и assets из `web/`. Не используй широкие шаблоны `go:embed`, способные захватить Markdown-файлы проекта.
11. Сохраняй чужие изменения в рабочем дереве. Перед каждой задачей проверяй `git status --short`; не исправляй и не удаляй несвязанные изменения.
12. После каждой задачи **CODE** запускай `gofmt` для затронутых Go-файлов, целевые тесты пакета и `go test ./...`. После задачи **TEST** зафиксируй ожидаемый красный результат целевого теста; ошибка должна соответствовать ещё не реализованному поведению, а не синтаксической ошибке теста. Статический guard, проверяющий уже существующую границу, не делай искусственно красным: докажи его отрицательную ветвь синтетическим fixture и оставь реальное дерево зелёным.
13. Не ослабляй тест для получения зелёного результата. Если тест ошибочно формулирует контракт `TZ.md`, исправь сам тест отдельным объяснённым изменением до production-кода.
14. Не объявляй задачу выполненной по результату чтения кода. Выполни указанные команды проверки и зафиксируй фактический результат.
15. Не добавляй отдельный log-файл, CLI проверки сценариев, открытие исходного сценария, SPA, CDN, worker pool, многопоточную обработку файлов, автоматическое исправление либо прикладное ограничение размера сценария.

## 4. Жёсткий стоп-кран внешней зависимости

Задача `G01` является обязательным шлюзом. Если на ней не удалось скачать, импортировать или скомпилировать закреплённый `dslparser`, немедленно останови выполнение всего плана. Оставь рабочее дерево валидатора без частичной реализации архитектуры. Сообщи:

- выполненную команду;
- точный текст ошибки без учётных данных;
- проверенный коммит;
- сведения о том, является ли причиной доступ к закрытому репозиторию, настройка Go/Git или несовпадение публичного API.

Не продолжай работу даже над пакетами, которые теоретически не зависят от парсера. Не создавай абстрактные интерфейсы «на будущее» и не имитируй типы парсера.

Тот же стоп-кран применяй, если модуль скачался, но на закреплённом коммите отсутствует заявленный в `TZ.md` публичный API. Не компенсируй несовпадение копированием внутренних типов или импортом `internal/...`.

## 5. Зафиксированные решения для недостающих деталей

Используй следующие решения; не переоткрывай их в ходе реализации:

- Пакет `web/` является Go-пакетом с именем `webassets`. Файл `web/assets.go` владеет единственной разрешённой package-level переменной `embed.FS`, помеченной `//go:embed` и не переназначаемой после инициализации. Он встраивает только `templates/*.html`, `assets/*.css` и `assets/*.js`.
- Все изменяемые runtime-состояния принадлежат экземплярам сервисов. Другие mutable globals запрещены.
- Unicode-helper публичного API имеет единственную сигнатуру `func SpanByRuneOffsets(text string, base Position, start, end int) (Span, error)`: `base` задаёт позицию первой rune переданного однострочного `text`, а `start` и `end` являются полуоткрытыми rune-индексами. Многострочный `text`, невалидная `base` и индексы вне диапазона возвращают ошибку.
- `internal/parseradapter` скрывает все типы `dslparser`. Его результат содержит либо готовые `validatorapi.Document` и `validatorapi.Context`, либо типизированную фатальную ошибку парсера, либо типизированный сбой вызова валидатора. Эти варианты взаимоисключающие.
- Внутренний контракт адаптера зафиксируй как `Adapter.ParseReader(io.Reader) Result`; `Result` содержит поля `Document validatorapi.Document`, `Context validatorapi.Context`, `Fatal *FatalIssue`, `Failure *Failure`. Не добавляй наружу исходный `error` парсера или его AST. Разреши pipeline определять свой узкий интерфейс с этим реальным методом для тестирования.
- Фатальная ошибка адаптера содержит только код и сообщение; диапазон для неё отсутствует. Сбой вызова содержит стабильный код `PARSER_CONTRACT_FAILURE`, `PARSER_UNEXPECTED_ERROR` или `PARSER_PANIC` и внутреннюю обёрнутую причину, но не stack trace для JSON.
- Production-реестр `Diagnostics/` поддерживает версию `1.1`, возвращает пустой список определений и успешно проходит `Validate()`. Механика выбора и проверки определений тестируется test-only наборами, передаваемыми во внутренний конструктор реестра.
- Сканер, pipeline, часы, генератор ID, открытие браузера и файловые операции получают узкие зависимости через конструкторы только после успешного шлюза `G01`. Эти интерфейсы описывают реальные операции подключённого приложения и не заменяют отсутствующий парсер.
- Одна HTTP-операция анализа выполняется в одной фоновой goroutine, чтобы polling и мягкая отмена оставались доступны. Внутри операции файлы и диагностические функции выполняются строго последовательно; сами диагностики goroutine не создают.
- Непрозрачные ID сценариев и отчётов генерируются заново при каждом сканировании через `crypto/rand`, кодируются `base64.RawURLEncoding` и разрешаются только через состояние текущего сканирования. В тестах генератор ID подменяется детерминированным.
- Фильтрация и сортировка отчёта имеют одну эталонную реализацию правил в Go для серверного fallback и тестов. JavaScript применяет те же правила локально к уже выведенным строкам. Без JavaScript отчёт и все записи остаются доступны.
- Windows-замена отчёта использует стандартную библиотеку и `MoveFileExW` с флагами из раздела 18 `TZ.md`; реализация выбирается build tags. Не используй `unsafe` и `golang.org/x/sys`.
- Невозможность определить системное имя часового пояса даёт `timezone: null`; числовое смещение всё равно сохраняется в RFC 3339 времени.
- Ошибка открытия даёт файловому результату операции `incomplete/opening`, fatal/contract/unexpected/panic парсера — `incomplete/parsing`. Ошибка сериализации или атомарной записи даёт результату текущей операции `incomplete/reporting`, но этот результат не записывается как новый JSON: старый валидный отчёт остаётся активным без изменения. Сбой отдельной диагностики при успешно завершившихся остальных стадиях даёт `completed_with_errors` и `failed_stage: null`.
- Используй HTTP-настройки: `ReadHeaderTimeout=5s`, `ReadTimeout=15s`, `WriteTimeout=30s`, `IdleTimeout=60s`, `MaxHeaderBytes=32 KiB`, form body не более `64 KiB`, shutdown timeout `10s`, polling interval `1s`.
- Поля форм зафиксируй так: `/workspace` принимает `path` и `version` со значениями `auto|1.1`; `/analysis/file` принимает только opaque `id`; `/analysis/all`, `/analysis/cancel` и `/shutdown` не принимают файловых данных. Report fallback использует query `level`, `source`, `category`, `sort`, `direction`.
- Успешные `/workspace`, `/analysis/file`, `/analysis/all` и `/analysis/cancel` отвечают `303 See Other` на соответствующую GET-страницу. Ошибка поля возвращает `400` с той же доступной страницей, неподдерживаемый метод — `405`, конфликт операции — `409`, неизвестный opaque ID — `404`. `/shutdown` сначала возвращает `200` со страницей подтверждения, затем инициирует остановку.
- Не добавляй CSRF-токен: локальная модель угроз из `TZ.md` требует строгой проверки `Host`, POST-only mutations, form limit и security headers.
- `/api/progress` возвращает только типизированный объект следующей формы:

  ```json
  {
    "state": "idle",
    "current_file": null,
    "total": 0,
    "processed": 0,
    "completed": 0,
    "completed_with_errors": 0,
    "incomplete": 0,
    "excluded": 0,
    "remaining": 0,
    "cancel_requested": false,
    "event_seq": 0,
    "message": null
  }
  ```

  `state` принимает `idle|running|completed|cancelled`; `current_file` и `message` nullable. `event_seq` увеличивается только для событий, разрешённых live-region в разделе 20.3 `TZ.md`.
- При shutdown менеджер сначала запрашивает мягкую отмену, не прерывает текущий файл, прекращает приём новых HTTP-запросов и ждёт завершения текущего файла в пределах общего timeout `10s`. Истечение timeout даёт `SHUTDOWN_FAILURE` и ненулевой exit code.
- Все пользовательские тексты интерфейса и документация пишутся по-русски. Технические JSON enum, коды и имена API сохраняются в форме из `TZ.md`.

- Скомпилируй минимальный probe, который импортирует именно `github.com/verdoga/dslparser` и ссылается на публичные функции, типы и экспортированные константы, перечисленные в разделах 2, 6 и 14 `TZ.md`.
- Через `go doc` или компиляцию проверь фактические сигнатуры `Parse`, `ParseString`, `ParseReader`, `Walk`, `FatalError`, `DiagnosticCode`, `Document`, `Node`, `Element`, `BlockInfo`, `Position`, `Span`, `Diagnostic`, `Cursor` и методов, используемых адаптером.

**Стоп:** при любой ошибке скачивания, аутентификации, импорта, компиляции или несовпадении необходимого публичного API выполни правила раздела 4 этого плана и не переходи к `G02`.

#### T04 — добавь архитектурные policy-тесты (**TEST**)

**Контекст:** `cmd/validator/architecture_test.go` как black-box тест всего module tree; разделы 3, 4, 6.3, 6.4, 7 и 23 `TZ.md`. Не создавай ради него новый production-пакет в корне.

**Сделай:**

- На базе `go/parser`, `go/ast`, `go/token` и `go/build` просканируй production `.go`-файлы модуля.
- Разреши импорт `github.com/verdoga/dslparser` только под `internal/parseradapter` и запрети `dslparser/internal/...` везде.
- Для production-кода `Diagnostics/` разреши только `<module>/validatorapi`, импорты собственных подпакетов `<module>/Diagnostics/...` из корневой композиции и стандартные `bytes`, `cmp`, `errors`, `fmt`, `maps`, `math`, `regexp`, `slices`, `sort`, `strconv`, `strings`, `unicode`, `unicode/utf8`; в `_test.go` дополнительно разреши `testing`. Рекурсивно применяй те же ограничения к каждому подпакету. Любое расширение allowlist потребует отдельного архитектурного решения. Запрети импорты файловой системы, сети, процессов, времени и случайности.
- Запрети в production-коде `Diagnostics/` операторы `go`, `init`, package-level `var` и регистрацию кодов из числового каталога.
- Запрети mutable globals во всём модуле, кроме единственной непереназначаемой `//go:embed` переменной типа `embed.FS` в `web/assets.go`.
- Проверь направленность импортов из раздела 4 `TZ.md` и отсутствие циклов через `go list`.
- Проверь, что embed-шаблоны охватывают только HTML/CSS/JS под `web/` и не охватывают `*.md`.
- Запрети в production-коде импорты `unsafe` и `reflect`, явные вызовы `panic` и контейнеры `map[string]any`/`map[string]interface{}` для структурированных данных.

**Красный результат:** тест должен обнаруживать намеренно добавленный test fixture-нарушитель либо быть table-driven с синтетическими исходниками; он не должен зависеть от наличия будущего production-кода.

**Готово, когда:** каждый тип нарушения доказуемо ловится отдельным под-тестом.

#### C05 — подключи архитектурные policy-тесты к реальному дереву (**CODE**)

**Контекст:** защита всех последующих задач.

**Сделай:**
